# 面向电信诈骗线索研判的可控智能体工作流系统设计与实现

## 摘要

电信网络诈骗线索初筛依赖人工阅读与经验判断，存在要素不全、结论缺少可核验依据、过程难以追溯三类问题；已有研究多聚焦诈骗文本分类精度，对"线索录入到人工复核完成"的状态管理、证据引用与失败语义讨论不足。本文设计并实现面向文本线索的可控智能体（Agent）研判系统：以有向状态图组织信息完整性检查、只读工具调用、草稿生成与人工审核，形成两个可持久化暂停点；以模型上下文协议（Model Context Protocol, MCP）封装文本检测与反诈知识检索两类只读能力，用工具白名单限定动作边界；以带定位的引用约束草稿表述，检测失败或无检索命中时执行失败即关闭（fail-closed）；以事件序号与数据库唯一键实现状态同步的幂等（Idempotency）。

系统采用 Vue 3 工作台、Spring Boot 业务后端、FastAPI 智能体服务、MCP 工具服务、Flask 检测服务与 MySQL 的分层结构，六容器经 Nginx 单一入口对外服务。智能体服务 27 项测试、Java 定向测试 17 项全部通过。120 条合成案例各重复 50 次，全部集与留出集的字段 F1、路由准确率、草稿结构合规率均为 1.0000；100 条检索查询上混合检索整体 Recall@1 为 0.83、Recall@3 为 0.97、Recall@5 为 1.00、MRR 为 0.8953，留出集为 0.50、0.90、1.00 与 0.6808。该结果反映规则抽取与检索排序在固定数据集上的可复现性，不等同于真实诈骗识别准确率。可用性仅完成一次自动化预演（成片 46 秒；脚本全程 2 分 40 秒，含约 45 秒录制停留），3 名真实用户测试尚未执行。

**关键词**：电信网络诈骗；智能体工作流；检索增强生成；人在回路；模型上下文协议；可恢复执行

## 第1章 绪论

### 1.1 研究背景

《中华人民共和国反电信网络诈骗法》自 2022 年 12 月 1 日施行，明确电信、金融、互联网主体的风险防控义务，将线索发现与前端劝阻置于治理链条显要位置[1]。基层收到的线索常以电话记录、聊天截图转写或群众口述进入系统，研判人员需判断联系渠道、自称身份、要求动作与发生时间四项要素，并回答风险等级的依据是否可核验、复核时能否还原判断过程。

人工流程的薄弱点有三：要素缺失需反复回访且记录散落；援引材料难以定位到具体段落与发布时间；多人流转缺少结构化留痕。大语言模型（Large Language Model, LLM）在文本归纳与工具调用上的进步为部分自动化提供条件，但直接让模型生成研判意见会引入新风险：可能编造法条与案例，可能在检测服务故障时输出低风险，也无法保证多轮补充后仍停留在同一条线索上。本文因此把既有检测能力与知识材料组织成可控、可恢复、可审计的流水线，只处理文本线索，不执行报警、冻结账户等有外部副作用的动作。

### 1.2 国内外研究现状

**诈骗文本检测**多为规则打分与基于 TF-IDF、朴素贝叶斯、支持向量机或预训练模型微调的分类方法，把问题定义为"给定文本输出风险标签"。这类工作在封闭测试集上指标较高，但输出为单一标量，既不说明缺少哪项关键信息，也不处理多轮补全。

**大语言模型推理与工具使用**方面，Chain-of-Thought 显式展开中间步骤以改善多步推理[3]；ReAct 把推理与行动交替组织，使模型调用工具并据返回值调整下一步[2]；Toolformer 以自监督方式让模型学会插入接口调用[8]。这类工作确立"模型决策、工具提供事实"的分工，但假设任务在一次会话内完成，对长事务中的暂停、恢复与人工介入讨论较少。

**检索增强生成**方面，Lewis 等把参数化记忆与非参数化索引结合，用检索结果约束生成[4]。检索侧，BM25 以词频饱和与长度归一化在短文本上保持稳定[5]；稠密段落检索（Dense Passage Retrieval, DPR）用双塔编码器映射查询与段落[6]；倒数排名融合（Reciprocal Rank Fusion, RRF）以排名合并多路结果，规避分数量纲不一致[7]。

**工程与安全**方面，LangGraph 提供基于检查点（Checkpoint）的中断与恢复[9]；MCP 把工具描述、参数模式与调用通道标准化，使契约可独立校验[10]。OWASP 列出提示注入（Prompt Injection）等大模型应用风险[11]，NIST 的人工智能风险管理框架及生成式分册强调可追溯性与人类监督[12][13]。

总体看，现有多轮暂停中的状态一致性、引用与结论的可核验绑定、工具故障时"不给出结论"的语义表达缺少系统处理，本文工作落在这些空隙上。

### 1.3 研究内容与贡献

1. **可控状态机工作流**：六个节点构成固定拓扑，"信息是否完整"是唯一分支条件，形成信息补充与人工审核两个持久化暂停点，补充轮次上限为 2；模型不参与编排，不能新增节点、工具或改变分支。
2. **只读工具契约与白名单**：经 MCP 暴露 `detect_text` 与 `search_knowledge`，参数由 JSON Schema 约束，客户端比对服务端工具清单，不一致即终止。
3. **带定位的引用与降级策略**：引用携带 `docId`、`chunkId`、`locator`、`publisher`、`sourceUrl`、`publishedAt`、`excerptType`，仅允许引用本次命中片段；无命中返回空引用；检测失败输出 `status=failed` 与 `riskScore=null`。
4. **事件驱动的状态同步**：每个可观察状态变化生成带序号事件，后端以 `(run_id, event_seq)` 唯一键与"仅接受下一个序号"实现幂等与乱序防护，终态不回退。
5. **可复现评测**：固定数据集版本与哈希，提供工作流与检索两套评测脚本，指标口径、样本数与命令一并归档。

检测模型训练、区块链存证与可视化属团队既有成果，本文只通过契约调用其文本检测接口。

### 1.4 论文结构

第 2 章介绍状态图工作流与检索融合等基础；第 3 章给出需求与验收场景；第 4 章描述架构、数据模型、状态机、事件幂等与权限；第 5 章说明实现细节；第 6 章报告评测并讨论局限；第 7 章给出可用性预演基线与待执行的用户测试方案；第 8 章总结与展望。

## 第2章 相关技术与理论基础

### 2.1 大语言模型与工具调用

模型在本文承担两类职责：把非结构化线索整理为结构化事实，判断材料是否足以支撑研判表述，输出固定字段的 JSON 并经模式校验后入库。工具调用（Tool Calling）指模型输出含工具名与参数的调用意图，运行时执行并回填结果。本文不让模型自由选择工具，而把调用固定在 `readonly_tools` 节点内，工具集合在代码中硬编码为两个字面量，模型即便被线索诱导也无法访问集合外能力。这对应 Saltzer 与 Schroeder 的故障安全默认值（fail-safe defaults）原则：访问权默认拒绝，仅显式授予者放行[14]。

### 2.2 状态图工作流与检查点

LangGraph 以有向图描述流程，节点是函数、边是转移条件，编译后的图对象持有运行状态[9]。**检查点**：编译时注入持久化存储（本文用 `AsyncSqliteSaver`），每次状态变更写入快照并以 `thread_id` 归属；本文以 `run_id` 作 `thread_id`，一次研判对应一条独立序列，不同案件不串状态。**中断**：节点内调用 `interrupt()` 时执行挂起，并把恢复所需的值写入检查点，外部通过 `Command(resume=value)` 送回输入；相比"存中间结果再重跑"，中断保留完整图状态，恢复时不必重放前序步骤。检查点位于持久卷，序列化启用严格模式（`LANGGRAPH_STRICT_MSGPACK=true`）以降低反序列化风险；SQLite 为单写者模型，故限定单实例、低并发部署。

### 2.3 模型上下文协议

MCP 定义工具服务与调用方之间的标准接口：服务端声明工具清单及参数模式，客户端列举并按模式调用[10]，本文使用流式 HTTP（Streamable HTTP）传输并挂载于 `/mcp/`。参数用 Pydantic 的 `Field` 约束长度与取值，越界请求在工具层即被拒绝；工具服务独立部署且无写权限，被注入操控时最大影响是多查一次资料。

### 2.4 检索模型与结果融合

检索对象为人工整理的 20 张反诈知识卡，每卡按段落切为一个检索单元；索引快照以内容哈希生成 16 位版本号，通过 `current` 与 `previous` 指针原子切换，支持回滚。BM25 对查询 $q$ 与文档 $d$ 的打分为

$$\text{score}(d,q)=\sum_{t \in q}\text{IDF}(t)\cdot\frac{f(t,d)\,(k_1+1)}{f(t,d)+k_1\left(1-b+b\cdot\frac{|d|}{\text{avgdl}}\right)}$$

实现取 $k_1=2.5$、$b=0.75$，逆文档频率用 $\ln\left(1+\frac{N-n_t+0.5}{n_t+0.5}\right)$ 以避免负值；$k_1$ 高于常用的 1.2，是考虑知识卡段落短、单段内关键词重复少，提高饱和上限可让命中多个不同关键词的段落拉开差距。TF-IDF 侧用稀疏词项向量的余弦相似度，词频取 $1+\ln f$，逆文档频率取 $\ln\frac{N+1}{n_t+1}+1$，按 L2 范数归一。RRF 只用排名，对每路结果中排名第 $r$ 的文档累加 $1/(k+r)$，取 $k=60$ 后降序输出，无需标定分数量纲。本文检索为纯词法检索，不含神经嵌入。

### 2.5 人在回路与失败语义

人在回路（Human-in-the-Loop, HITL）的关键不是"让人点按钮"，而是让人在信息充分时做不可逆决策。本文把审核设为图中的中断节点，审核者可见完整草稿、检测结果与逐条引用，可执行通过、修改、退回，修改范围限于四个非证据字段。

失败语义需显式设计：检测服务错误时若沿用下游默认值（`riskScore=0`、`riskLevel=检测失败`），上游会把"没有结果"读成"低风险"。适配层因此把错误归一为 `status=failed`、`riskScore=null` 并附错误码，草稿状态降为 `PARTIAL`，前端以"检测未成功"替代风险等级展示，即 fail-closed。

## 第3章 需求分析

### 3.1 角色与场景

| 角色 | 标识 | 主要操作 |
|---|---|---|
| 线索研判员 | `ROLE_WORKER` | 创建案件、提交线索、回答补充、查看草稿与引用、发起提审 |
| 审核管理员 | `ROLE_ADMIN` | 查看待审草稿、通过/修改/退回、查看检测记录 |
| 系统维护人员 | `ROLE_ADMIN` | 查看运行状态与错误码、维护知识索引、轮换服务凭证 |

主场景为：研判员录入线索，系统检查四项关键信息；齐备则调用检测与检索，生成带引用草稿并进入待审核；不齐备则暂停列出具体问题，补充后从暂停点继续；审核管理员复核后通过、修改或退回。

### 3.2 功能需求

| 编号 | 优先级 | 需求 |
|---|---|---|
| FR-01 | 高 | 创建线索案件：校验内容非空且不超过 10000 字符，生成案件编号 |
| FR-02 | 高 | 检查信息完整性：指出四项缺项并生成追问，补充后继续同一案件 |
| FR-03 | 高 | 调用既有检测能力：经受控工具调用，保留原始响应与调用状态 |
| FR-04 | 高 | 检索反诈知识：返回 Top-K 片段，无命中时返回空依据 |
| FR-05 | 高 | 生成结构化草稿：摘要、检测结果、引用、待核实信息、建议步骤、不确定性说明 |
| FR-06 | 高 | 展示引用来源：引用可定位到段落，检测、引用与归纳三者可区分 |
| FR-07 | 高 | 人工审核：通过/修改/退回，保存审核人、结论与意见，修改限四字段 |
| FR-08 | 高 | 暂停与恢复：两个暂停点的状态与上下文可持久化 |
| FR-09 | 高 | 运行轨迹：可查节点、工具、状态、耗时、错误码 |
| FR-10 | 高 | 失败提示与降级：显示失败步骤，不伪造分数或引用 |
| FR-11 | 中 | 知识材料维护：保留来源、时间、版本与许可状态 |
| FR-12 | 中 | 评测运行与报告：导出指标、失败样例与运行清单 |

### 3.3 非功能需求

**安全与隐私**：工具白名单仅开放只读能力；线索与检索文档视为不可信输入，不得改变工具权限；记录按归属校验，跨用户读取返回 403；审核人与创建人必须分离；日志只记摘要与哈希。

**可恢复性**：每次运行有唯一 `run_id` 与明确状态；超时、上游不可用、响应格式无效以不同错误码区分；两个暂停点均须覆盖"中断—重启—恢复"测试。

**可追溯性**：知识依据可回查到当前索引版本的具体段落；检测结果关联到工具调用记录；评测报告记录数据集哈希、索引版本与指标口径。接口采用异步受理（202）加轮询查询，外部服务耗时单独统计。

### 3.4 验收场景

验收覆盖八类场景：线索完整且服务可用时生成可回查的草稿；缺关键字段时暂停追问并在补充后续办同一案件；知识库无相关内容时明确说明无依据；检测工具超时时标记失败且不输出分数；工具参数越界时由工具层拒绝并记录；审核退回后进入待修订并关联原意见；线索含提示注入时仍只调用白名单工具；越权读取他人案件时拒绝并记录审计信息。

## 第4章 系统设计

### 4.1 总体架构

| 层次 | 组件 | 职责 | 关键实现 |
|---|---|---|---|
| 展示层 | Vue 3 工作台 | 建案、补充、草稿与引用、审核、轨迹 | `views/agent/AgentWorkspace.vue`、`components/agent/` |
| 业务层 | Spring Boot 2.5 | 鉴权、持久化、派发与对账 | `AgentController`、`AgentRunService`、`AgentRunDispatcher` |
| 编排层 | FastAPI 智能体服务 | 工作流执行、检查点、MCP 客户端、事件发布 | `main.py`、`workflow.py`、`mcp_client.py` |
| 工具层 | MCP 工具服务 | 仅暴露 `detect_text`、`search_knowledge` | `mcp_tools.py` |
| 能力层 | Flask 检测服务、知识索引 | 风险打分、知识卡检索 | `flask_app/app.py`、`retrieval.py` |

调用链为：浏览器携 JWT 访问后端；后端生成 `run_id`，以共享凭证调用 `/internal/v1/runs`；智能体在 `readonly_tools` 节点经 MCP 调工具；工具访问 Flask 的 `/api/detect/text` 或读取索引快照；状态变化回调至 `/internal/agent/v1/runs/{runId}/events`。检查点只承载恢复所需的最小上下文，业务表承载用户可见状态与审计事实，查询以 MySQL 已确认状态为准。

### 4.2 数据模型

| 表 | 作用 | 关键字段与约束 |
|---|---|---|
| `agent_case` | 线索案件 | `case_no` 唯一、`user_id`、`content`、`status`，索引 `(user_id,status,created_at)` |
| `agent_run` | 单次运行 | `run_id` 唯一、`case_id`、`status`、`last_event_seq`、`input_hash`、`result_json`、`error_code` |
| `agent_event` | 事件轨迹 | 唯一键 `(run_id,event_seq)`、`event_type`、`payload_json`、`occurred_at`、`received_at` |
| `agent_review` | 人工审核 | 唯一键 `run_id`、`reviewer_id`、`decision`、`comment`、`edits_json` |
| `agent_supplement` | 补充记录 | 唯一键 `(run_id,round_number)`、`answers_json`、`user_id` |

一个案件对应多次运行，一次运行对应多条事件、至多一条审核与多条补充记录；多次运行不覆盖历史结果，退回后重新研判生成新的 `run_id`。迁移脚本 `V001`—`V003` 均用 `CREATE TABLE IF NOT EXISTS` 与幂等插入，首行声明 `SET NAMES utf8mb4`，避免容器按 latin1 解析导致中文双重编码。`input_hash` 用于识别同一 `run_id` 携带不同文本的冲突，命中返回 409。

### 4.3 智能体状态机与双暂停点

| 节点 | 处理 | 分支 |
|---|---|---|
| `check_missing_information` | 规则匹配四项信息，含否定词排除 | 有缺项且轮次 < 2 转 `request_information`，否则转 `readonly_tools` |
| `request_information` | `interrupt()` 挂起等补充 | 校验字段名、轮次、长度后回填文本 |
| `readonly_tools` | 并行调用检测与检索 | 任一失败保留另一结果 |
| `build_draft` | 组装固定结构草稿与不确定性说明 | 检测失败置 `FAILED` |
| `wait_for_review` | `interrupt()` 挂起等审核 | 通过/修改/退回 |
| `finalize_review` | 合并可修改字段，写终态 | 退回 `RETURNED`；检测成功 `COMPLETED`，否则 `PARTIAL` |

状态转移为 `RUNNING` →（缺项）`WAITING_FOR_INFO` → `RUNNING` → `WAITING_FOR_REVIEW` → `COMPLETED`/`PARTIAL`/`RETURNED`。案件状态表示业务生命周期，运行状态表示单次执行，取值相同而语义不同。

暂停是图的属性而非业务层休眠，挂起期间不占执行线程，也不依赖内存会话。恢复须匹配前置条件：补充请求声明 `round`，与检查点中 `supplementRound` 不符返回 409；审核请求要求运行处于 `WAITING_FOR_REVIEW`。补充轮次上限为 2，超出后剩余缺口由草稿的"待核实信息"承载。

否定词是分支判断的关键细节：线索写"对方没有要求转账"时，"转账"仍会命中关键词，从而误判为已提供要求动作。实现对每个字段维护否定模式（如"没有要求/未要求/没有索要"），命中词前 20 个字符内出现否定模式则跳过，该规则由评测集 `negated_claims` 类别覆盖。

### 4.4 事件与幂等

`eventSeq` 按当前补充轮次 $r$ 取号：启动事件固定为 1，等待补充与工具步骤完成取 $2+r$，等待审核取 $3+r$，终态取 $4+r$，同轮次内严格递增，跨轮次不回退。

后端接收分四步：字段完整性校验，缺 `eventSeq`、`status` 不在允许集合、`payload` 或 `occurredAt` 为空即返回 400；幂等判定，`(run_id,event_seq)` 已存在或序号不大于 `last_event_seq` 时返回 `duplicate` 且不推进；终态保护，已处于终态的运行拒绝后续事件；顺序校验，要求 `event_seq == last_event_seq + 1`，出现缺口即拒绝，由智能体重发或对账补齐。重复事件被唯一键拦截，乱序事件被拒而非静默覆盖；回调失败有限次重试，仍失败标记 `CALLBACK_FAILED`。派发侧同样幂等：补充与审核接口先落库，返回 `idempotent=true` 时不再派发。

### 4.5 权限模型

**浏览器到后端**：沿用 JWT，令牌置于 `token` 请求头，服务端校验签名与有效期，登出后写入 Redis 黑名单，登录限流 10 次/分钟。`caseId` 与 `runId` 不作为权限凭证，每次读取按归属过滤：研判员只见本人案件，管理员可查看全部但不得审核本人创建的案件，违反返回 403。

**后端到智能体**：使用共享凭证 `AGENT_SERVICE_TOKEN`，经环境变量注入，不进入代码、前端包与日志，缺失或不匹配返回 401；智能体不映射宿主端口，仅后端可达。

**智能体到工具**：客户端维护 `ALLOWED_TOOL_NAMES = {detect_text, search_knowledge}`，连接后比对服务端 `list_tools` 声明，不一致即中断本次运行；工具只读，不提供写库、发消息或执行代码的能力。

## 第5章 系统实现

### 5.1 关键流程

**启动与执行**：`POST /agent/cases` 在事务内写入 `agent_case` 与 `agent_run`（`CREATED`），提交后异步派发；派发失败由 `markDispatchFailed` 置 `FAILED` 并补写 `dispatch.failed` 事件。`start_run` 先查 `run_states`，同一 `run_id` 且 `input_hash` 一致返回既有状态，哈希不同返回 409；新任务以 `asyncio.create_task` 执行，接口立即返回 202。

**中断与上报**：`_report_workflow_result` 检查返回值中的 `__interrupt__`；挂起原因为 `supplement` 时发布 `run.waiting_for_info` 并携带问题列表；无中断时先发布 `step.completed`（含检测结果与工具轨迹），再发布 `run.waiting_for_review`（含草稿与引用），审核完成后发布 `run.finished`。

**恢复与收尾**：`_resume_suspended_run` 读取检查点快照，终态直接返回既有状态，挂起类型不匹配返回 409，补充请求还需比对轮次；校验通过后调用 `resume_workflow`。终态事件确认后删除该 `run_id` 的检查点（`adelete_thread`），减少敏感原文留存。

### 5.2 提示约束与引用定位

提示遵循三条约束：只使用给定的检测结果与检索片段；不补充材料外的法条、案例或统计数字；信息不足时输出"不足以判断"而非推测。草稿约束为 9 个必需字段：`caseId`、`runId`、`status`、`summary`、`detection`、`citations`、`missingInformation`、`suggestedChecks`、`uncertaintyNotes`。

引用字段与检索结果一一对应：`docId` 与 `chunkId` 为索引快照的确定性标识（由文档标识、段落序号与内容哈希派生），`locator` 记录段落定位，`publisher`、`sourceUrl`、`publishedAt` 供外部核验，`excerptType` 标注摘录或转述。本文知识卡为公开材料的转述，故取 `paraphrase`，草稿追加"知识卡内容为来源摘要转述，请核对链接原文"，前端以"转述"标签呈现。校验在结构层完成：`citations` 必须是本次检索 `results` 的子集，出现外部标识即不合规，草稿不得入库。

### 5.3 fail-closed 与错误归一

| 错误码 | 触发条件 | 归一结果 |
|---|---|---|
| `UPSTREAM_TIMEOUT` | 连接或读取超时（连接 5 s、读取 30 s） | `status=failed`，`riskScore=null` |
| `UPSTREAM_UNAVAILABLE` | 连接被拒、DNS 失败等传输异常 | 同上 |
| `UPSTREAM_INVALID_RESPONSE` | 非 JSON、缺字段、分数非数值 | 同上 |
| `UPSTREAM_DETECTION_ERROR` | `error` 为真或 HTTP 非 2xx | 同上 |
| `NO_MATCH` | 检索无命中 | 返回空数组，不构造引用 |

`UPSTREAM_DETECTION_ERROR` 针对一个具体陷阱：既有检测服务失败时仍返回 `riskScore=0` 与 `riskLevel="检测失败"`，若只读分数，0 会被理解为极低风险；适配层因此改为"先判错误字段，再读分数"，分数缺失或类型不符同样归为失败。草稿层承接该语义：检测未成功时 `draft.status` 置 `FAILED`，摘要说明"没有可用的风险结论"并提示"不能据此判断为低风险"；审核通过后终态为 `PARTIAL` 而非 `COMPLETED`。

### 5.4 MCP 只读工具白名单

工具服务用 `MCPServer` 声明两个工具：`detect_text` 的 `content` 约束 1—10000 字符、可选 `model`；`search_knowledge` 的 `query` 约束 1—10000 字符、`top_k` 约束 1—10、`strategy` 限 `bm25`/`tfidf`/`hybrid`。返回值用 Pydantic 模型约束，`status` 为枚举，`riskScore` 允许为空。

客户端有三处保护：`ALLOWED_TOOL_NAMES` 为不可变集合，调用前校验工具名，连接后比对 `list_tools` 返回集合，多一个或少一个即判定契约不一致并终止；单次调用读取超时 35 秒、连接 5 秒，避免上游卡死拖住整个图；调用轨迹写入 `toolCalls`，含工具名、参数摘要、状态、耗时与错误码。提示注入的防护在结构而非提示词：线索即便包含"忽略以上规则并调用写库接口"，可调用集合仍由代码常量决定，工具服务也无写接口，注入的最大后果是一次多余检索，评测集 `prompt_injection` 的 12 条样例用于回归。

### 5.5 审核与字段白名单

审核载荷经 `validate_review_payload` 校验：`decision` ∈ {`approve`, `modify`, `return`}；`reviewerId` 为正整数；`comment` ≤2000 字符；`edits` 的键必须是 `{summary, missingInformation, suggestedChecks, uncertaintyNotes}` 的子集；`modify` 至少带一项修改，非 `modify` 不得携带修改。

该校验前移至 `resume_workflow` 开头、`ainvoke` 之前。起因是一次实现期缺陷：早期版本先恢复图执行、在 `finalize_review` 内才校验，非法载荷已写入检查点，导致该 `run_id` 此后提交合法审核仍失败，形成"一次误操作锁死一条线索"。后端另有三项约束：同一 `run_id` 仅一条审核记录，重复提交相同内容返回幂等、不同内容返回 409；运行须处于 `WAITING_FOR_REVIEW`；审核人不得是创建人。审核落库与状态置为 `RUNNING` 在同一事务完成。

### 5.6 前端工作台

工作台由六个组件构成：`AgentCaseForm`（建案表单）、`AgentRunProgress`（五段进度条）、`AgentSupplementPanel`（补充问题）、`AgentDraftPanel`（草稿与引用卡片）、`AgentReviewPanel`（审核面板）、`AgentRunTimeline`（运行轨迹）。

进度条按"受理 → 补充 → 研判 → 待审核 → 完成"呈现，当前段高亮、已完成段打勾，两个暂停点可区分。引用卡片展示序号、发布方、发布时间、定位符与出处编号（`chunkId` 前 12 位）并给出原文链接，标签标注"转述"或"摘录"。待审核时草稿区右上角出现"去提审"按钮，点击直达复核面板；已有任务时新建表单隐藏；窄屏切单列。联调中修正三处缺陷：`agent.service` 配置误嵌在 `files` 节点下导致派发与回调全部 401，已移至 `application.yml` 根节点；恢复测试把合法恢复写在异常断言内导致假通过，已移出并断言终态；初始化脚本缺 `SET NAMES utf8mb4` 致中文角色名双重编码，已补齐并以十六进制校验。

### 6.5 检索评测设计与结果

检索数据集为 100 条模板查询，按 80/20 划分，每条标注一个 gold 来源卡标识；知识库含 20 张来源卡与 20 个检索单元。三种策略共用同一索引快照与查询集，每查询重复 3 次取中位数计时。Recall@K 为前 K 条出现标注来源卡的查询占比，MRR 为首个命中位置倒数之均值，未命中记 0。

### 6.6 结果讨论与局限

**指标偏乐观。** 三项 1.0000 需放在数据性质下理解：评测数据由模板生成，表达与规则词表同源。结果证明"规则实现与规格一致"，而非"规则覆盖真实口述的多样性"；方言、错别字、语音转写断句与口语化时间未进入数据集，真实数据上字段召回率预期明显低于 1.0。

**留出集 Recall@1 偏低。** 混合检索留出集 Recall@1 为 0.50，半数查询的首位不是标注来源卡。原因有二：纯词法检索无法把"客服退款"与"冒充电商客服办理退款"映射到同一词项；知识库仅 20 个单元，Recall@5 达 1.00 很大程度是库容所致，扩展后大概率下降。当前检索宜作候选依据召回，是否引用仍需人工判断。

**外部依赖。** 摘要与表述依赖外部大模型接口；评测时为避免网络与费用波动，草稿构造使用固定 fixture，真实模型调用未纳入指标。结构校验置于输出之后（字段齐备、类型正确、引用来自本次检索），兜住下限。

**未验证项。** 进程被强制终止后的卷恢复、真实检测服务故障注入与渗透测试仍未执行，检查点恢复只验证同一 SQLite 文件重开后的续办；人工引用支持率尚未开展。

## 第7章 可用性评估

### 7.1 评估目的与方法

评估关注三点：新用户能否在三分钟内独立完成一次线索提交；是否理解两个暂停点并知道下一步点哪里；草稿中的引用出处是否足以支撑复核判断。

评估分两步：先用无头浏览器脚本走通闭环，验证界面元素、状态流转与前端报错，取得耗时基线；再按任务卡与量表收集真人的主客观数据。截至目前，**3 名真实用户的测试尚未执行**，本节只报告预演基线、发现的问题与待执行方案，不对真人可用性下结论。

### 7.2 自动化预演基线

预演环境为六容器编排，入口 `http://localhost`（Nginx 同源反代 `/api`），Chromium 无头模式、视口 1440×900、慢速模式 200 ms，账号为演示研判员与演示管理员各一，用例为虚构的"冒充公检法要求转账至安全账户并索要验证码"。

| 时间点（成片） | 事件 |
|---|---|
| 0:00–0:04 | 打开登录页，输入演示研判员账号与口令 |
| 0:05–0:12 | 登录后进入"线索研判"，选择来源"电话记录"并录入线索文本 |
| 0:13 | 提交线索 |
| 0:16 | 状态变为"等待补充信息"（首轮 5.1 秒），进度条停在 25% 的"信息补全"段 |
| 0:17–0:22 | 填写并提交补充信息 |
| 0:24 | 状态变为"等待人工审核"（2.0 秒），生成 5 条带定位符与出处编号的知识引用，风险分 100 |
| 0:28–0:36 | 退出研判员账号，以管理员账号登录 |
| 0:37–0:45 | 通过"去提审"进入复核面板，选择"通过"并填写审核说明 |
| 0:46 | 状态变为"已完成"（2.0 秒），进度 100%，执行轨迹 5 条 |

对外成片 46 秒；原始脚本执行全程 2 分 40 秒，其中约 45 秒为录制刻意加入的停留，故该数字是脚本执行时长，不是真人操作时长。从提交线索到进入待审核约 15 秒（成片 0:13 至 0:24），含一次补充交互与两轮编排；人工复核从提交到完成约 2 秒。全程控制台错误为 0，无非预期 4xx/5xx；五段进度条在两个暂停点表现正确，每条引用均带定位符与出处编号，"去提审"入口与"已有任务隐藏新建表单"按设计生效。

### 7.3 预演发现的问题

核心问题是补充问题的格式约束不透明：时间字段只接受时间表达，回答"对方用语音联系我"会被重复追问，说明规则抽取的可解释性未传递到交互层。改进方向是在追问旁展示判定依据，例如"未识别到时间表达，可填写'今天上午十点左右'"。其余为工程性问题：角色切换需退出重登（约 30 秒）、引用卡片首屏信息密度偏高、首次登录未强制修改默认口令。

### 7.4 待执行的三人测试方案

**被试与安排**：招募 3 名背景互补的被试——1 名有反诈或客服经验者、1 名无相关经验的办公人员、1 名技术背景人员，记为 P1、P2、P3。单场 20—25 分钟，含知情同意、12 分钟任务、5 分钟量表与访谈。主持人仅在被试卡住 60 秒后提问"界面上有什么线索可以帮助你"，不直接指出路径。全程录屏，仅用编号。

| 编号 | 任务 | 完成判据 | 观察点 |
|---|---|---|---|
| T1 | 登录并进入线索研判页面 | 看到建案表单与进度区 | 是否找到菜单入口 |
| T2 | 把一段电话记录提交研判 | 出现进度条且状态非"执行中" | 是否注意到提交按钮 |
| T3 | 系统要求补充时补上已知情况并继续 | 状态进入"等待人工审核" | 是否理解暂停原因 |
| T4 | 在草稿中找出任一条结论对应的知识出处 | 能指出引用编号与来源链接 | "转述"标签是否被理解 |
| T5 | 换管理员账号将线索审核通过 | 状态变为"已完成" | 是否找到"去提审" |

**记录指标**：任务完成率（无需主持人接管即达判据的比例）、单任务用时（从念完任务到判据达成的秒数）、错误数（误点、重复提交、字段填错致返工）、求助次数与系统可用性量表（System Usability Scale, SUS）得分。SUS 为 10 题五点量表，奇数题正向、偶数题反向，折算公式为 `SUS = [(奇数题得分和 − 5) + (25 − 偶数题得分和)] × 2.5`，高于 68 视为高于行业中位水平[15]。记录表按被试一行、任务一列组织，测试前留空。

**判定门槛（建议值）**：任务完成率 ≥ 90%；T2 与 T3 平均用时各 ≤ 90 秒；SUS 均值 ≥ 70；高优先级问题全部有明确处置。门槛在测试前确定，避免事后调整；完成上述步骤前，不得以"经过 3 人测试验证"表述本系统可用性。

## 第8章 总结与展望

### 8.1 工作总结

本文围绕"线索录入—能力调用—带依据草稿—人工复核—过程留痕"完成以下工作。架构上，确立浏览器只访问业务后端、智能体与工具服务仅容器内网可达的信任边界，用三层凭证分开用户身份、服务身份与工具权限。流程上，六个节点构成固定拓扑状态图，信息补充与人工审核做成可持久化中断点，轮次上限为 2。证据上，引用绑定到文档、段落与索引版本，无命中返回空引用，检测失败输出空分数，阻断"失败被读成安全"。同步上，带序号事件配合唯一键与顺序校验，实现至少一次投递下的幂等写入与终态保护。

### 8.2 不足与展望

**评测数据需人工核验**：数据集为模板合成且与词表同源。后续应对 150—200 条脱敏真实线索双人标注并计算一致性，再重跑指标。

**缺少对照实验**：需补齐单轮大模型基线与"仅检测"基线，在同批样本上比较结论可用性、引用支持率与人工修改量。

**检索受限于词法匹配**：留出集 Recall@1 为 0.50，同义表达是主要瓶颈。可把稠密向量检索作为独立变量加入，与 RRF 结果分开报告。

**部署与恢复仍受限**：SQLite 检查点只适合单实例，多副本需换用支持并发写入的后端；进程被强制终止、卷挂载异常与磁盘写满尚未覆盖，应引入故障注入，验证"事件已发出但未确认"的中间态。检查点含线索原文，需明确保留期限与访问控制。

**能力边界有意收窄**：系统不含多智能体协作、自动处置与模型微调。若接入处置动作，须先把工具扩展为带审批的两阶段写入，并保留可撤销窗口。
