# 反诈线索研判 Agent 毕设项目策划案

> 文档状态：题目与范围已按指导老师意见确认；进入详细设计阶段  
> 项目基础：宿舍比赛项目“AI反诈骗检测系统”  
> 本人目标岗位：AI Agent 应用开发

## 1. 项目概述

### 暂定题目

**面向电信诈骗线索研判的可控智能体工作流系统设计与实现**

### 项目背景

现有比赛项目已经提供文本、语音、图像检测、综合风险评估和文本 LLM 语义分析能力。当前 LLM 能力属于检测流程中的一个分析层，尚未形成可暂停、可恢复、可调用多种业务工具的 Agent 工作流。

本毕设拟在现有系统之上新增独立的 Agent 研判模块：复用已有检测接口，结合可追溯的反诈知识检索，完成线索整理、工具调用、依据汇总和人工审核。系统输出作为辅助研判材料，不替代人工判断，也不自动执行转账拦截、报警等外部操作。

### 核心问题

如何让 Agent 在反诈线索研判中按明确流程调用受限工具、给出可追溯依据，并在信息不足、工具失败或需要复核时安全暂停和恢复？

## 2. 项目目标与个人贡献

### 项目目标

1. 交付一个可运行的 Agent 应用模块，并接入现有反诈检测系统。
2. 让 Agent 能调用检测和知识检索工具，返回结构化、带来源的研判草稿。
3. 支持追问补充、人工审核、流程追踪、失败处理和审核后恢复。
4. 建立可复现的评测集，比较 Agent 工作流与单轮 LLM 基线的表现。

### 本人负责

- 设计并实现 Agent 工作流和案件状态管理。
- 实现 MCP 工具接入，封装现有检测接口与反诈知识检索。
- 实现 RAG 检索、引用来源展示、人工复核和运行轨迹页面。
- 编写 Agent 场景评测集、评测脚本、测试报告和论文中的系统实验部分。

### 团队职责边界

- 室友 1：诈骗文本识别模型、训练数据和分类效果评估。
- 室友 2：检测结果的证据存证与可视化。
- 本人：Agent 工作流、工具调用、知识检索、人工复核和 Agent 效果评测。

现有检测能力仅作为被调用的工具，不把团队已有模型、存证模块或可视化模块写成本人的新增成果。复用代码、数据和接口前，应与组员及指导老师确认授权、署名和论文说明方式。

## 3. 用户与核心场景

### 目标用户

需要对疑似诈骗信息进行初步整理和核查的校园反诈工作人员或系统演示人员。

### 核心场景

用户提交一段疑似诈骗短信或聊天记录。Agent 检查信息是否完整，调用现有文本检测接口，并检索相关反诈知识条目。随后系统生成包含检测结果、引用依据、待核实问题和建议核查步骤的研判草稿。用户可补充信息、修改草稿或确认完成；遇到缺少关键信息、引用不足或工具异常时，系统明确提示并暂停或降级处理。

## 4. 个人负责功能与验收标准

| 编号 | 功能 | 具体行为 | 验收标准 |
|---|---|---|---|
| F1 | 线索建档 | 创建案件，录入线索文本、来源和补充背景，生成案件编号 | 能创建、查看和继续处理案件；输入缺失时给出明确提示 |
| F2 | 受控工具调用 | Agent 通过 MCP 调用已有文本检测和反诈知识检索工具 | 工具具有固定名称及参数结构；非法参数被拒绝；工具超时有明确状态 |
| F3 | 反诈知识 RAG | 对整理后的公开反诈材料进行检索，保留文档、发布机构、日期和段落信息 | 每条引用均能定位到实际文档及段落；无匹配内容时明确说明未检索到依据 |
| F4 | Agent 工作流 | 按状态执行信息检查、工具调用、结果汇总、引用校验和草稿生成 | 流程步骤可追踪；输出符合约定 JSON/数据结构；不把模型猜测伪装成检测结果 |
| F5 | 人工复核与续办 | 支持补充信息、审核、修改、退回，并在审核后恢复流程 | 暂停前状态能够保存；用户提交审核意见后可从对应节点继续 |
| F6 | 执行轨迹与失败处理 | 展示运行状态、工具名、耗时、成功/失败码、来源引用及重试结果 | 能定位失败步骤；错误不会被伪装成正常低风险结果；不记录模型隐藏思维链 |
| F7 | 效果评测 | 对 Agent 工具使用、引用质量、任务完成和运行性能进行离线评估 | 提供评测数据、指标定义、基线对比和可复现报告 |

### Agent 输出结构

- 案件编号与输入摘要
- 已有检测接口返回的结果及其来源
- 检索到的知识依据：文档、段落、发布时间或版本
- 初步研判摘要、待补充信息和建议核查步骤
- 不确定性说明、审核状态和运行编号

输出应区分“检测接口结果”“知识库依据”和“Agent 汇总内容”，避免把生成文本当成事实或模型预测。

## 5. 系统边界

### 本期纳入

- 单个 Agent 编排工作流，不建设多智能体群聊或自主代理网络。
- 两类只读工具：现有文本检测、反诈知识检索。
- 一个受控流程：线索录入、信息检查、工具调用、引用汇总、人工复核和结果保存。
- 基础运行日志、超时重试、失败提示和审核后续办。
- 基于脱敏或合成样例的离线评测。

### 本期不纳入

- 重新训练或改进诈骗分类模型。
- 重做语音、图像识别、区块链存证、数字水印和现有仪表盘。
- Agent 自动报警、联系用户、冻结账户或执行其他外部副作用操作。
- 无边界联网搜索、任意代码执行、开放式数据库写入和复杂长期记忆。
- 为追求复杂度而增加多 Agent、微调大模型或自建大规模语料平台。

## 6. 技术方案

### 推荐架构

```text
Vue 前端
  └─ 案件录入、研判结果、引用查看、审核与运行轨迹
       ↓ REST API
Spring Boot 后端
  └─ 用户鉴权、案件接口、权限检查、Agent 请求转发
       ↓ REST API
Python Agent 服务
  ├─ LangGraph 工作流、案件状态、人工暂停与恢复
  ├─ MCP Client：连接受控业务工具
  └─ 结果结构校验与运行记录
       ↓ MCP
反诈工具适配层
  ├─ 文本检测工具 → 现有 Flask AI 服务
  └─ 知识检索工具 → 反诈文档索引
```

现有 Python 检测服务和其 Docker 运行环境保持独立。Agent 服务采用单独的依赖和容器，避免为新增 Agent 能力改变原检测服务的运行环境。工具适配层的部署形态在技术设计阶段确认；原型阶段可单独运行，保持 MCP 接口可测试。

### 工作流草图

```text
提交线索
  → 输入校验与案件结构化
  → 判断信息是否缺失 ── 是 → 请求补充并暂停
  → 调用文本检测与知识检索
  → 汇总结果并校验引用
  → 生成研判草稿
  → 人工审核/修改
  → 保存最终结果与运行记录
```

### 关键技术约束

- MCP 工具采用固定名称、输入输出结构和参数校验；初始只开放只读操作。
- Spring Boot 负责用户身份和请求权限，Agent 服务不绕过后端鉴权直接暴露给浏览器。
- 每次运行设置超时和调用上限；失败时返回明确错误或部分结果，不填造默认风险分数。
- RAG 数据记录来源、版本和段落定位；展示的引用必须能回查原始材料。
- 日志保留流程状态和工具结果，不保存不必要的个人敏感信息或模型隐藏思维链。
- 密钥仅从环境变量或部署密钥配置读取，不写入代码、提交记录或论文截图。

## 7. 评测与验证计划

### 评测集设计

建议建立约 100–200 条经人工核验的场景，覆盖常见诈骗线索、信息不全、多轮补充、知识库无匹配、相互矛盾的材料、工具超时和提示注入等情形。数据使用合成或脱敏内容，并记录每个样例的预期工具、可引用资料和审核要点。

### 对照方案

- 基线 A：现有检测接口结果。
- 基线 B：单轮 LLM 直接生成研判摘要。
- 实验组：加入 MCP 工具调用、RAG 引用和人工复核的 Agent 工作流。

### 评测指标

- 任务完成率、必需信息抽取正确率。
- 工具选择准确率、参数结构有效率、工具失败后的正确降级率。
- 引用可定位率及人工标注的引用支持准确率。
- 输出结构有效率、人工审核通过/修改比例。
- 平均及 P95 响应时延、单次模型调用量或费用估算。

评测报告应同时呈现失败案例和边界条件，不只报告平均成功率。具体指标阈值由预实验和指导老师意见确定，不在立项阶段预先宣称实验结果。

## 8. 软件开发迭代安排

每轮按“需求确认 → 设计接口和验收条件 → 实现一个可演示的端到端切片 → 自动化测试与人工评审 → 记录问题并决定下一轮”的流程推进。优先保证完整闭环，再增加可靠性和评测能力。

| 迭代 | 工作内容 | 阶段交付与退出条件 |
|---|---|---|
| I0 需求与立项 | 与指导老师确认题目、个人贡献、复用边界、用户场景和最终演示要求 | 题目与职责经确认；形成需求清单、流程图和功能验收标准 |
| I1 最小闭环 | 创建 Agent 服务骨架；从前端提交一条线索，后端转发并调用现有文本检测接口 | 能完成一次请求并返回结构化结果；失败有明确错误 |
| I2 工具与 RAG | 实现 MCP 工具定义、知识文档整理、检索和引用元数据 | 检测工具和检索工具可独立调用；输出引用能回查文档段落 |
| I3 工作流控制 | 加入缺失信息判断、状态保存、人工暂停/恢复、超时和重试 | 中断后可继续；工具失败不产生伪造结果；流程步骤可追踪 |
| I4 产品化界面 | 增加案件页、研判页、引用详情、审核交互和运行轨迹 | 用户能完成录入、查看、补充、审核和续办闭环 |
| I5 评测与交付 | 构建评测集、对照基线、运行测试、部署演示、整理论文材料 | 提供指标报告、失败案例、部署说明、演示脚本和个人贡献说明 |

每轮开始前列出本轮要完成的用户行为和验收条件；结束时进行演示，记录未完成项及原因。未通过验收的流程不进入下一轮扩展。

## 9. 风险与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 选题与近年 Agent、RAG 或防诈骗管理题目相近 | 立题审核可能要求调整 | 强调反诈线索研判、受控工具编排、人机审核和可量化评测；请老师最终确认相似度 |
| 团队项目代码和个人贡献边界不清 | 论文贡献难以说明 | 在任务书、代码模块、提交记录和论文中分别记录复用部分与新增部分 |
| LLM API 不稳定或费用受限 | 演示和评测受影响 | 支持 Mock 模型与固定测试响应；记录模型、参数和调用异常；保留本地可运行流程 |
| 知识材料来源不可靠或引用错位 | 研判依据不可信 | 只纳入可追溯公开材料；保留文档版本和段落编号；评测引用支持准确率 |
| Agent 被输入内容诱导越权 | 产生不安全工具调用 | 工具白名单、参数 schema、只读权限、服务端权限校验和人工审核；对抗样例纳入评测 |
| 项目范围过宽 | 关键闭环无法按期完成 | 先做文本线索和两种工具；语音/图像、复杂部署和多 Agent 均为后续候选项 |

## 10. 交付清单与完成定义

### 交付物

- 需求与功能验收说明、系统架构图和 Agent 工作流图。
- Agent 服务、MCP 工具适配层、后端接口和前端研判页面。
- 脱敏/合成评测集、自动评测脚本和实验结果报告。
- Docker 部署说明、接口文档、演示脚本和论文材料。

### 项目完成定义

1. 一条线索能够从录入经过检测与知识检索，形成可审核的结构化研判草稿。
2. 每条引用可定位到知识文档；检测结果与 Agent 汇总内容明确区分。
3. 信息补充和人工审核可以暂停并恢复流程。
4. 超时、非法参数和工具不可用均有可追踪的处理结果。
5. 评测结果可复现，包含基线对比、定量指标和失败样例。
6. 论文能够清楚说明本人新增模块、团队复用模块及其边界。

## 11. 下一步

1. 将已确认的题目、复用边界、文本 MVP 和评测要求落实到需求规格。
2. 完成架构、接口、状态/数据模型、安全边界和评测脚本的详细设计。
3. 设计评审通过后，按 I1 开始最小可运行闭环；本阶段不预填任何实验分数。
