## 2. 测试目标与用户角色

| 角色 | 典型身份 | 关键任务 |
| --- | --- | --- |
| 线索研判员（ROLE_WORKER） | 反诈中心坐席、社区民警 | 录入线索、回答补充问题、核对带出处草稿 |
| 审核管理员（ROLE_ADMIN） | 值班组长、业务主管 | 复核草稿、通过/退回、查看检测记录 |
| 系统管理员（ROLE_ADMIN） | 平台运维 | 用户与角色管理、导出、排障 |

本次关注三个问题：

1. 新用户能否在 **3 分钟内**独立完成一次线索提交；
2. 用户是否理解"等待补充信息"和"等待人工审核"两个暂停点，并知道下一步点哪里；
3. 草稿里的引用出处是否足以支撑人工复核判断。

## 3. 测试方法

### 3.1 形式

- 单场 20～25 分钟：5 分钟说明与知情同意、12 分钟任务、5 分钟 SUS 问卷与访谈。
- 主持人不提示操作路径，只在被试完全卡住 60 秒后给予中性提示（"界面上有什么线索可以帮助你？"）。
- 全程录屏 + 记录任务完成情况、求助次数、用时与错误。

### 3.2 任务卡

| 编号 | 任务描述（念给被试） | 完成判据 | 观察点 |
| --- | --- | --- | --- |
| T1 | 用发给你的账号登录系统，进入"线索研判"页面 | 看到建案表单与进度区 | 是否找到菜单；首屏是否理解要做什么 |
| T2 | 把这段电话记录提交给系统研判 | 出现进度条且状态非"执行中" | 是否注意到"提交并开始研判"；是否被表单校验卡住 |
| T3 | 系统要求补充信息时，把你知道的情况补上并继续 | 状态进入"等待人工审核" | 是否理解为何暂停；是否知道需要全部填写 |
| T4 | 在草稿里找出任意一条结论对应的知识出处 | 能指出引用编号与来源链接 | 引用卡片是否易读；"转述/摘录"标签是否理解 |
| T5 | 换管理员账号，把这条线索审核通过 | 状态变为"已完成" | 是否找到"去提审"；是否理解通过与退回的差别 |

### 3.3 指标定义

- **任务完成率**：无需主持人接管即达成判据的比例。
- **用时**：从主持人念完任务到判据达成的秒数。
- **错误**：误点、重复提交、填错字段导致返工等可观察的偏离。
- **求助次数**：被试主动提问或明确表达"不知道下一步"的次数。
- **SUS**：10 题李克特 5 级量表，按标准公式折算 0～100 分，>68 视为高于行业中位。

## 4. 本次自动化预演

### 4.1 环境

- 部署：`docker compose` 六容器（MySQL 8 / Redis 7 / Spring Boot / FastAPI Agent / Flask AI / Nginx）
- 入口：`http://localhost`（Nginx 同源反代 `/api`）
- 浏览器：Chromium headless，1440×900，慢速模式 200 ms
- 账号：`demo_worker`（研判员）、`admin`（管理员）
- 用例：冒充公检法要求转账到"安全账户"并索要验证码

### 4.2 时间线（脚本耗时，非真人）

| 时间点 | 事件 |
| --- | --- |
| 0:00 | 打开登录页 |
| 0:07 | 登录成功，进入仪表盘 |
| 0:16 | 进入"线索研判"工作台 |
| 0:20 | 开始填写线索（来源：电话记录） |
| 0:27 | 填写完成，20 秒后提交 |
| 0:30 | 提交线索 |
| 0:35 | 状态变为"等待补充信息"（Agent 首轮 5.1 秒） |
| 0:43 | 提交补充信息 |
| 0:45 | 状态变为"等待人工审核"（2.0 秒），生成 5 条引用 |
| 0:45–1:03 | 浏览草稿、引用卡片与出处编号 |
| 1:28 | 研判员退出登录 |
| 1:34 | 管理员登录并打开同一任务 |
| 1:45 | 点击"去提审"，填写审核意见 |
| 1:46 | 提交审核 |
| 1:48 | 状态变为"已完成"（2.0 秒） |
| 1:48–2:08 | 查看仪表盘总览 |
| 2:08–2:40 | 回到已完成任务，展示 100% 进度与 5 条执行轨迹 |

### 4.3 观察结果

1. 进度条五段（受理 → 补充 → 研判 → 待审核 → 完成）在两次暂停处表现正确，当前段有高亮、已完成段有勾选。
2. 草稿区每条引用都带序号、发布方、发布时间、定位符（locator）与"出处编号"（chunkId 前 12 位），并给出原文链接。
3. "去提审"按钮在待审核状态出现并直达复核面板，无需自行寻找。
4. 已有任务时新建表单自动隐藏，避免误覆盖当前任务。
5. 全程 console error 为 0，网络请求无非预期 4xx/5xx。

## 6. 3 人测试执行清单

1. **招募**（建议 3 人覆盖不同背景）：1 名有反诈/客服经验者、1 名无经验办公人员、1 名技术背景人员。
2. **准备**：独立账号各 1 个（研判员），1 个管理员账号由主持人持有；准备 3 段不同手法的线索文本（冒充公检法 / 刷单返利 / 冒充客服退款）。
3. **执行**：按 3.2 任务卡逐条执行；全程录屏；使用 3.4 表格记录。
4. **收尾**：SUS 问卷 + 3 个开放问题（最困惑的一步、最想保留的功能、最想删掉的信息）。
5. **产出**：回填本报告第 4、5 节，计算平均完成率、平均用时与 SUS 均值，附 1～2 段关键片段截图。
6. **判定门槛（建议）**：任务完成率 ≥ 90%，T2/T3 平均用时 ≤ 90 秒，SUS ≥ 70，P1 问题全部有明确处置。

## 附录 A：SUS 量表（中文版）

1 = 非常不同意，5 = 非常同意。奇数题正向计分，偶数题反向计分。

1. 我愿意经常使用这个系统。
2. 我觉得这个系统过于复杂。
3. 我认为这个系统很容易使用。
4. 我需要技术人员帮助才能使用这个系统。
5. 我觉得系统各部分功能整合得很好。
6. 我觉得系统中有太多不一致的地方。
7. 我认为大多数人能很快学会使用这个系统。
8. 我觉得这个系统用起来很别扭。
9. 我对使用这个系统很有信心。
10. 我需要先学很多东西才能开始使用这个系统。

折算公式：`SUS = (奇数题得分和 - 5) + (25 - 偶数题得分和)`，再乘以 2.5。
